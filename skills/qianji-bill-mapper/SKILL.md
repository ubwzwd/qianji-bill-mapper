# 银行账单 → 钱迹 CSV 映射

把用户上传的银行/信用卡账单（PDF 或图片）解析出每一笔交易，映射进钱迹 App 的标准导入模板，输出一个可直接导入的 CSV 文件。

## 输出模板（13 列，顺序固定，必须一字不差）

```
时间,分类,二级分类,类型,金额,账户1,账户2,备注,账单标记,手续费,优惠券,标签,账单图片
```

空白模板与示例见 `assets/template.csv`。生成的 CSV 必须用 **UTF-8 with BOM** 编码（钱迹要求，否则中文乱码），用 `\r\n` 换行。

## 工作流

### 第 0 步：确定账户和币种

开工前确认两件事：

1. **账户（账户1）填什么？** 先读 `references/accounts.md` 里用户预存的信用卡/银行账户列表，把相关账户**列出来让用户选**（如「这份是哪个账户的账单？1. <信用卡A> 2. <储蓄卡B> …」），不要让用户每次手敲。
   - 若账单抬头/卡号能和列表里某账户对上，可直接判断并和用户确认一句即可。
   - 若 `references/accounts.md` 还没建立或为空，按「账户列表的初始化与维护」一节先帮用户建好，再继续。
   - 用户也可随时说「加一张卡 / 改个名字 / 删掉某账户」来维护这个列表（见同一节）。
2. **账单的语言 / 币种是什么？** 影响金额解析（小数点 vs 千分位）和备注语言。能从账单直接看出（如全程 SGD）就不必多问，确认一句即可。

如果用户上传时已经说明了账户和币种，就不用重复问。

### 第 1 步：读取账单

按文件类型读取：

- **PDF**：先用 `pdftotext`（poppler）试抽文本。文本型 PDF 直接抽；扫描型/图片型 PDF 走 OCR（`pytesseract` + `pdf2image`/`pdftoppm` 光栅化）或把页面转成图片后用视觉读取。
- **图片**（jpg/png 等）：能直接在上下文里看到就直接视觉读取交易表格；否则用 `pytesseract` OCR 辅助。

> 若你的运行环境自带文件读取/PDF 解析能力（例如 Claude.ai 的 `file-reading` / `pdf-reading` 技能），优先用它；没有时按上面的命令行工具处理。

把每一笔交易的原始字段都抓出来：日期、（可能有的）时间、摘要/商户/备注、金额、借贷方向/正负号、（可能有的）余额。

### 第 2 步：逐笔映射到 13 列

对每一笔交易，按下面规则填列：

**时间** — 格式 `YYYY/M/D H:MM`（如 `2022/7/12 21:20`）；`-` 分隔也可（`2022-7-12 21:20` / `2022-07-12`）。
- 账单只有日期没有时间时，时间部分留空，只写 `2022/7/12`。
- 注意账单的日期格式可能是 DD/MM/YYYY 或 MM/DD/YYYY，结合上下文（如出现 >12 的日数）判断，拿不准就向用户确认，不要猜错月日。

**类型** — 钱迹支持 5 种：`收入` / `支出` / `报销` / `转账` / `还款`（信用卡还款）。填其他值视为无效。判定：
- 银行账单的借方/扣款/Debit/负号/`-` → `支出`
- 贷方/存入/Credit/正号/`+` → `收入`
- **还款 / GIRO**：信用卡账单里的「还款 / payment / GIRO / thank you」，或银行卡账单里给信用卡的还款扣款 → 用 `还款` 类型。
  - ⚠️ **方向不固定，要看这笔在当前账单上是入账还是扣款**：还款是「账户1（出钱方）→ 账户2（收钱方/信用卡）」。
    - 在**信用卡账单**里，还款是钱**进卡**（贷方/括号金额），本卡是收钱方 → 本卡填 **账户2**，账户1 = 出钱的银行账户（问用户或查账户列表）。
    - 在**银行卡账单**里，同一笔 GIRO 是钱**出账**（借方/扣款），本银行卡是出钱方 → 本卡填 **账户1**，账户2 = 被还的信用卡。
  - 同一笔还款如果两张账单都导入会重复，提醒用户注意（一般只在其中一张账单里记一次）。
- **本人账户间划转**（提现到本人卡、转入余额宝/理财、ATM 取现）→ `转账`，按上面同样的方向逻辑判断本账户该放账户1（转出）还是账户2（转入）。
- **报销**：能明确认出是垫付后收到的报销款时用 `报销`；否则当收入处理。
- **保守原则**：分不清是不是还款/转账/报销时，按支出/收入处理即可，不要乱标。但信用卡账单里的「还款 / GIRO」是高频且明确的场景，应当用 `还款`，不要错记成支出。

**金额** — 永远填**正数**（绝对值），方向由「类型」决定。去掉货币符号和千分位逗号。
- ⚠️ 若该笔有「手续费」或「优惠券」，金额列**必须包含**手续费/优惠券金额（钱迹的规则，否则对不上）。

**分类 / 二级分类** — 自动推断；映射规则见 `references/categories.md`。
- 只能用参考表里的中文分类名，禁止自创。
- 注意：若同时填了「分类」和「二级分类」，钱迹会以「二级分类」为准覆盖；填二级分类时确保一级分类对应正确。
- 转账/还款的分类、二级分类一律留空。
- **拿不准的分类要先问用户，不要自作主张也不要静默留空**：把所有「无法有把握归类」的交易**汇总成一个清单**，在生成最终 CSV **之前**一次性问用户该怎么归（见第 3 步），等用户回复后再填。这是用户的明确要求。
  - 「拿不准」包括：商户名是看不懂的代码/缩写（如 `POS 6231****`、`PAYNOW`）、介于两个大类之间、能看出大类但分不清二级分类等。
  - **二级分类单独拿不准**时（一级明确、二级不明），可以只把二级列进清单问，或一级照填、二级留空——按对用户最省事的方式，但仍要在小结里点出来。

**账户1** — 收入/支出填账单所属账户（第 0 步从账户列表选定的那个）；转账/还款时填**出钱方**账户（见上方方向逻辑）。

**账户2** — 仅 `转账` / `还款` 时填，填**收钱方**账户（转入的卡、被还的信用卡）；其余留空。本账户是出钱方还是收钱方，取决于这笔在当前账单上是扣款还是入账。

**退款（重要固定规则）** — 账单上的**贷方/括号金额/负号**若是商户退款（如电商退货、撤单），记成 `收入` 类型、分类 `退款`，金额填正数，备注注明来源（如「Shopee 退款」）。不要和真正的还款/转账混淆。

**外币交易（固定规则）** — 金额用账单**结算货币**（如 SGD）的本地金额；原始外币金额写进**备注**（如 `ZGY Klang 吃饭（马来西亚 MYR 336.40）`）。钱迹按单一币种记账，不要把外币原值填进金额列。

**备注** — 用账单里的商户名/摘要原文，清理掉收单机构噪音编号让它更可读，保留用户能认出这笔钱花在哪的信息。外币按上一条在备注标原币种金额。

**账单标记** — 默认留空；如需「不计入」，值必须是 `不计收支`(或 `nc`)、`不计预算`(或 `nb`)、`不计收支&预算`(或 `nc&nb`) 之一。

**手续费** — 仅 `转账` / `还款` 类型支持；填了的话「金额」必须已包含手续费。其余情况留空。

**优惠券** — 仅非 `收入` 类型支持；填了的话「金额」必须已包含优惠券金额。其余情况留空。

**标签** — 默认留空。如要写多个标签，用 `#` 分隔（如 `麦当劳#老婆#旅行`）。注意：**仅钱迹会员**支持模板导入标签；带 emoji 的标签可能乱码。

**账单图片** — 默认留空；如有则填图片链接（多张用 `,` 连接）。

### 第 3 步：把拿不准的分类汇总后问用户（生成 CSV 之前）

第 2 步逐笔映射时，凡是**无法有把握归类**的交易，先**别急着填分类、也别静默留空**，而是收集起来。把它们整理成一个清单一次性问用户，**等用户回复后再进入第 4 步生成 CSV**。

呈现清单时要让用户好回答：
- 按商户/摘要分组，相同商户合并成一条问（如「`STARBUCKS` 共 4 笔，归到哪类？」），不要同一个商户问很多遍。
- 每条给出：商户/摘要、笔数、金额或日期范围、你**倾向的猜测**（如「我猜是 餐饮，但不确定二级」），让用户确认或改。
- 给出可选分类范围（取自 `references/categories.md`），方便用户直接选。
- 如果拿不准的项很多，按金额从大到小排，优先确认大额；零星小额可建议用户统一归「其他」或留空。

用户回复后，把答案填回对应交易。用户若说「这些就留空」或「都归其他」，照办即可。

**综合电商平台要逐笔确认（重要）**：像 **Shopee、Lazada、淘宝、京东、Amazon、PayNow** 这类账单上只显示平台名、看不出具体买了什么的交易，**不要笼统归成「消费购物」**——同一个平台的不同笔可能分散在打车充值、猫砂、饮料、泳具等完全不同的大类。要把这些交易**逐笔列出（日期+金额）请用户说明买的是什么**，再据此归类；用户明确说不知道的那几笔才留空。

### 第 4 步：用脚本生成 CSV

不要手写 CSV 字符串（容易在编码、逗号转义、BOM 上出错）。把每一笔交易整理成一个 JSON 数组（键名用中文列名，缺的字段不写即可），存成 `transactions.json`，然后用本技能自带的脚本写出 CSV——它会强制 13 列、UTF-8 带 BOM、`\r\n` 行尾，并对**缺类型、负金额、转账/还款缺账户2、金额非数字**等问题打印提醒：

```bash
python scripts/write_qianji_csv.py transactions.json qianji_import.csv
```

输出路径按运行环境定：本地（Claude Code / Codex / 普通终端）直接写到当前工作目录即可；Claude.ai/API 环境写到 `/mnt/user-data/outputs/` 这类可供下载的目录。脚本路径相对本技能目录，必要时用绝对路径。

`transactions.json` 示例：

```json
[
  {"时间": "2024/3/5", "分类": "餐饮", "二级分类": "午餐", "类型": "支出",
   "金额": "28.50", "账户1": "招商银行", "备注": "肯德基"},
  {"时间": "2024/3/6", "类型": "收入", "金额": "8000",
   "账户1": "招商银行", "分类": "工资", "备注": "3月工资"}
]
```

**务必查看脚本打印的提醒并人工核对可疑项**（尤其方向/金额）。

> 若脚本不可用，可退而用 Python `csv` 模块内联写出，但同样要保证 `encoding='utf-8-sig'`、`newline=''`、列顺序严格按模板、空字段写 `''`。

### 第 5 步：交给用户检查

生成后，把 CSV 文件交给用户（Claude.ai/API 用 `present_files`；Claude Code / Codex / 终端环境直接告诉用户文件路径或给出下载方式），并附一段简短小结：
- 一共解析了多少笔交易、时间范围、合计支出/收入。
- 第 3 步问过、已按用户意见归类的交易；以及最终仍留空分类的交易（如有），让用户知道可在钱迹里再补。
- 如果有任何金额/日期/方向你不确定的交易，逐条点出来请用户核对，不要默默处理掉。

## 账户列表的初始化与维护

为了不用每次手敲账户名，用户的信用卡和银行账户清单预存在 `references/accounts.md`。

**初始化（首次使用，或文件为空时）**：主动问用户「请把你的信用卡和银行账户都列一下（钱迹里叫的名字）」，把回答写进 `references/accounts.md`，分「信用卡」和「银行/储蓄账户」两类列出。

**导入时**：读这个文件，把账户列成可选项让用户选（见第 0 步），不要让用户手打。能从账单卡号/抬头对上某账户时，直接确认一句即可。

**维护**：用户随时可以说「加一张 XX 卡」「把 A 改名叫 B」「删掉 XX」，相应更新 `references/accounts.md`。若技能已打包安装为只读，则把文件复制到可写处修改后重新打包。

## 重要原则

- **不丢交易、不重复**：账单里有几笔就输出几笔，对一下数量和合计金额。
- **金额方向可疑时宁可问**：把钱算反（支出当收入）比留空更糟。
- **不编造**：账单里读不出的信息不要脑补填进去。OCR 不清楚的数字要标出来让用户确认，不要猜。
- **隐私**：这是用户的私人财务数据，只用于本次转换，不要写进备注之类会暴露的地方（如完整卡号——只保留必要的可读信息）。
